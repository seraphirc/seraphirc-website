    Getting Started

    Welcome

    SeraphIRC is an IRC client for Linux, Windows, and iOS/macOS. It talks to networks directly, or through a Soju or ZNC bouncer, and it keeps the classic feel while carrying modern protocol support.

    What it does

    AreaWhat you get
    Multi-networkDirect networks, bouncer imports, channels, server windows, and private messages in one workspace, each network independent of the others.
    BouncersFirst class Soju support with network discovery, chat history, and read markers that sync across devices. Existing ZNC setups keep working. No bouncer at all is fine too.
    IRCv3SASL, server-time, account tags, away-notify, echo-message, batch, and chat history negotiated where the network offers them. IRCv3 functionality continues to expand, and is updated on the website as new features arrive.
    FormattingMarkdown and token syntax compiled to standard IRC control codes, so other clients see ordinary bold, italics, and color.
    File transferBouncer uploads, classic DCC, and Seraph Transfer, an encrypted peer to peer send that works from behind a bouncer and behind NAT.
    AppearanceA collection of prebuilt themes, a theme editor, and imports from the community marketplace.
    PrivacyNo analytics, no account requirement, no cloud dependency. The client talks to your networks and nothing else.

    Getting Started

    Connecting to a Network

    A network is a saved configuration: address, port, nickname, TLS, and how to authenticate. SeraphIRC can keep as many connected as you like.

    Saving a network

    Networks are created in the Network Manager rather than by command. It holds the server address and port, TLS, your nickname and alternates, SASL and NickServ credentials, service targets, and the channels to join automatically.

    Passwords go to the operating system's credential store, never into the config file in plain text.

    Going up and down

    The connection commands act on whichever network the current window belongs to.

    CommandWhat it does
    /connectConnect the active network, or link to a different server
    /disconnectDrop the connection immediately
    /reconnectCycle the connection
    /quitLeave properly, with an optional parting message
    /nickChange your nickname on the connected network

    Authenticating

    SASL happens during registration, before you are visible on the network. Prefer it where the network supports it. NickServ authentication happens after connecting, by messaging the service. Both are per network and both read from secure storage.

    To talk to NickServ by hand use /ns rather than /msg NickServ. It routes to the configured service target, so a mistyped nickname cannot leak your password.

    Networks are independent. #linux on two networks means two windows, with separate history, unread state, and member lists.

    Getting Started

    Channels and Conversations

    Channels are group rooms, queries are one to one, and the server window is where the network talks to you. All three are buffers.

    Finding and joining

    /join #channel joins and opens the window. /list opens a searchable channel list rather than dumping thousands of lines into the server window. /part leaves, /cycle rejoins in one step, and /partall clears the board.

    Talking to one person

    /query nick opens a private window. /msg nick message sends one line, which suits bots and quick replies. /notice is the quieter form that bots are expected not to answer. /me sends an action.

    Who is that

    /whois nick asks the server for somebody's account, host, idle time, and shared channels. /whowas answers for somebody who has left.

    Query windows show whether the other person is authenticated and on which account. A green check means verified. An orange question mark means unauthenticated or unknown.

    Turning the volume down

    /ignore nick hides somebody on the current network, and it persists. /accept is stronger, managing the server side caller ID list so private messages never reach you unless you allowed the sender. /notify does the opposite and tells you when somebody comes online.

    Ignore List and Notify List cover both in full. To quiet a whole channel rather than a person, see Per-Buffer Settings.

    Running a channel

    IRC commands covers /op, /voice, /kick, /ban, /kickban, /topic, and /mode. Most take an optional channel, so you can moderate from another window.

    Getting Started

    Using a Bouncer

    A bouncer stays on IRC when your computer is not, then replays what you missed. SeraphIRC handles the two common ones natively and works fine without either. Connection details are saved once as a bouncer profile.

    Soju

    The deepest support. Networks import from the bouncer, bouncer networks are discovered through soju.im/bouncer-networks, and you manage them without leaving the client. History comes back over chathistory, read markers sync across devices through MARKREAD, and mobile push arrives over soju.im/webpush.

    ZNC

    Existing setups keep working, including the usual user/network login. /znc forwards a command to ZNC itself rather than the network behind it, which is how you reach *status and the modules.

    Direct networks

    No bouncer is a normal way to use SeraphIRC. Connect straight to the network and everything behaves the way a classic client does. DCC is available here, where a bouncer would rule it out.

    Behind a bouncer, the address other clients see belongs to the bouncer, not to you. That is why plain /dcc is unavailable there, and what Seraph Transfer was built to solve.

    Getting Started

    Sending Files

    Three routes. Which one you want depends on whether you are behind a bouncer and whether the file may touch a third party. Each has its own settings page under Network.

    Seraph Transfer

    /seraphtransfer nick offers a file over a direct, mutually authenticated TLS 1.3 connection. No upload host, no copy left behind, and unlike DCC it works from behind a bouncer and behind NAT. The same action sits in a nickname's right click menu.

    /seraphchat nick is the conversational version: a direct encrypted chat outside the network.

    DCC

    /dcc is the classic transfer, computer to computer with no server between. It needs a direct connection, so it is unavailable through soju or ZNC. Incoming offers also appear as cards in the window and in the transfers panel. DCC chat is not supported.

    Bouncer uploads

    If your soju bouncer has uploads enabled, hand it a file and share the link. This one goes through a host, which is the price of working with anyone regardless of client.

    Drag, drop, and paste

    Files can be dragged in or pasted, including onto a window that does not have focus, and the drop lands where you aimed it.

    Interface

    Appearance

    Theme, fonts, density, and how the message pane is drawn. Settings > Interface > Appearance.

    Theme

    Pick a built-in theme, or one of your own. Clone a built-in and the copy appears under Your themes, editable in the theme editor while staying a layer over the stock theme rather than a replacement for it.

    Themes other people made import from Settings > Interface > Appearance > Import Theme. The theme marketplace holds the community submitted ones, each checked by hand and credited to the nick that sent it in.

    If a theme leaves the interface unreadable, press Ctrl+Shift+R to restore the default appearance (Cmd+Shift+R on macOS). Undo is offered afterwards.

    Transcript Layout

    ModeDraws
    ClassicThe traditional IRC layout. Timestamp, nickname, and message on one line.
    ModernThe default. Nickname and time above the message, with consecutive messages from one person grouped under a single header.

    Render IRC avatars in Modern Mode shows the avatar of anyone who has published one through IRCv3 metadata, instead of the colored initial. Off by default, because it loads each image from whatever server that person chose, which tells that server your IP address.

    Your avatar address is published to every network supporting IRCv3 metadata, so other people can see it. It must be an https:// link. Leave it empty and press Publish to remove it. Anyone whose client has no avatar support simply will not see it.

    Fonts

    The interface font and the message font are set separately, family and size each, from the fonts installed on your system. Both start at system-ui at 15px.

    Interface

    Sounds and Alerts

    The global switches live in Settings > Interface > Sounds & Alerts. Every buffer can then be tuned on its own from Buffer Settings.

    The four switches

    SettingDefaultWhat it does
    Enable desktop notificationsoffSystem pop-ups. These only fire when the buffer is not focused, so the window you are reading never pops at you.
    Enable soundsonThe alert chime. Plays whether or not the buffer is focused.
    Notify on private messagesonAlerts for queries and direct messages.
    Notify on nick mentionsonAlerts when your nick appears in a channel.

    The same page has a Preview button that plays the bundled notification sound, so you can check it is audible without waiting for someone to talk to you.

    What never alerts

    • History replay. A chathistory fill can deliver hundreds of messages at once, and none of them ping.
    • Your own messages, including the echo back from the server.
    • Anyone on the ignore list for that network.
    • Bouncer service consoles such as BouncerServ, *status, and *sasl. They routinely echo your own nick back at you, which is not a mention.

    Transfers make noise too

    DCC and Seraph Transfer starting and finishing, and Seraph Chat invites, ride the same Enable sounds switch. Each one is announced once, so a progress tick cannot chime twice.

    The mentions inbox

    Nick mentions also collect in the @ inbox in the top bar, up to the last 20. A mention that arrives in the buffer you are already looking at is recorded as read.

    Desktop notifications are off out of the box. The first time you turn them on, the operating system may ask for permission.

    Chatting

    Aliases

    An alias is a short name for a longer command. Manage them in Settings > Chatting > Aliases, or from the composer with /alias.

    Making one

    /alias j /join means /j #seraphirc works from then on. /unalias j removes it. Running /alias with no arguments opens the settings page, which has the same two fields plus Edit and Delete on every row.

    Arguments are appended

    An alias is a prefix, not a template. Whatever you type after it is added to the end of the target command. There are no numbered placeholders.

    The aliasYou typeWhat runs
    /alias kb /kickban/kb Alice flooding/kickban Alice flooding
    /alias mods /msg #staff/mods need a hand/msg #staff need a hand
    /alias afk /away/afk/away

    Naming rules

    • The leading slash is optional and the name is lowercased, so /J and j save the same alias.
    • No spaces in the name.
    • The target gets a leading slash if you leave it off, so /alias j join works.
    • Built in commands and built in aliases cannot be overwritten, so an alias can never shadow something the client already does.

    Names already taken

    These nine ship with the client, alongside every command name itself.

    AliasRuns

    Chaining

    An alias may point at another alias. Expansion stops after five hops and reports an expansion loop rather than spinning. An alias pointing directly at itself is refused when you save it.

    Where they live

    Aliases are stored in your client config, so they apply on every network and survive a restart. They travel with Settings > Application > Import/Export Config, merging into whatever is already there, and an imported alias wins a name collision.

    Aliases resolve locally before anything is sent, so nobody on the network sees the short form. /kb Alice flooding reaches the server as an ordinary kick and ban.

    Chatting

    Chat Logging

    SeraphIRC keeps a searchable local history of your conversations. Nothing is uploaded. The controls live in Settings > Chatting > Chat Logging.

    Where it goes

    Messages are written to a SQLite database inside the client's data folder on your own machine. Settings > Application > Diagnostics has an Open Data Folder button if you want to look at it.

    This log is also what fills your windows again after a restart, so turning logging off for a buffer means that buffer starts empty next time you launch.

    Enable All Logging

    On by default. The checkbox sets the default for new buffers only. Channels, queries, and server windows that already exist keep whatever setting they have, so switching it off does not retroactively silence anything you are already in.

    Per buffer

    Every buffer carries its own Enable Logging switch under Buffer Settings. That is the one to reach for when a single channel should not be written down.

    Turning logging off never deletes anything. Messages already saved stay saved until you clear them. See Exporting and Clearing.

    Not the same as diagnostics

    Chat logs are your conversations. Diagnostic logs are connection behavior and client state, kept separately under Settings > Application > Diagnostics. Clearing one never touches the other.

    Chatting

    Exporting and Clearing

    Logs come out as plain text, and they can be deleted whole or one buffer at a time.

    Exporting everything

    Settings > Chatting > Chat Logging has four collect buttons. Each opens a save dialog and writes a .tgz archive. A button is disabled when there is nothing of that kind to export.

    ButtonArchive
    Collect Server Logsseraphirc-server-logs.tgz
    Collect Query Logsseraphirc-query-logs.tgz
    Collect Channel Logsseraphirc-channel-logs.tgz
    Collect All Chat Logsseraphirc-all-logs.tgz

    What is inside

    One plain text file per buffer, filed by kind and network: 

    channels/Libera/#seraphirc.log
queries/Libera/Alice.log
server/Libera/server.log

    Each line carries its timestamp, the sender, and the text.

    [2026-08-15T09:14:02Z] <alice> morning
[2026-08-15T09:14:20Z] [action] <bob> waves

    Ordinary messages get the first form. Anything that is not a normal message carries its type in a second bracket.

    Exporting one buffer

    Right click a buffer in the treebar and choose Export Logs. That writes a single .log file for that buffer instead of an archive, named for the network and the buffer, as in Libera-#seraphirc.log.

    Clearing

    ActionReach
    Clear Logs, on the settings pageDeletes server, channel, and query logs on every network, and empties those windows on screen.
    Clear Logs, on a buffer's right click menuDeletes the stored history for that one buffer and empties it on screen.
    /clearClears what is on screen only. The logs are untouched.

    Both Clear Logs actions ask first, and neither touches your diagnostic log history.

    /clear and /clearall are the safe pair. They tidy the view without deleting anything you might want later.

    Chatting

    Ignore List

    Silence a nickname, or a whole hostmask that a nick change cannot escape. The list is per network and lives at Settings > Chatting > Ignore List.

    Adding an entry

    /ignore Alice from the composer, Ignore from a nickname's right click menu, or the settings page, which also lets you pick which network the entry belongs to. /unignore removes one.

    Entries are masks

    A bare nick loses to /nick troll2, which is the first thing anyone does once they work out they have been ignored. So an entry is parsed as an IRC mask, nick!user@host, and each part is matched with wildcards. * spans any run of characters and ? matches exactly one.

    You typeIt meansCatches
    trolltroll!*@*That nick only, until they change it
    troll*troll*!*@*troll, troll2, troll_away
    *@spam.example*!*@spam.exampleEveryone from that host
    *!*@spam.exampleThe same thing, spelled in fullEveryone from that host

    A nick pasted out of the member list keeps its mode glyph, and @troll is read as the nick rather than as a host mask. Entries cannot contain spaces, since no part of a mask can.

    Remove an entry the way you added it. /unignore Alice does not clear a *!*@spam.example that happens to cover her.

    What an ignore hides

    Text only ignores just move the traffic, so the entry covers all of this.

    • Messages and actions.
    • Notices, which is the next thing reached for once messages stop landing.
    • CTCP requests.
    • Invites, which are otherwise the cheapest way to put attacker chosen text on your server window.
    • Their joins, parts, quits, and nick changes.

    The member list still tracks them correctly. Only the lines are suppressed, because inferring channel membership from what was displayed is how a user list ends up with ghosts in it.

    Syncing across devices

    On a soju bouncer an ignore travels. Ignore someone at the desk and your phone has them ignored too, and unignoring travels back the same way. It rides soju's soju.im/blocked key, so a device that was asleep catches up on reconnect, and soju stops sending push notifications from anyone on the list.

    Two conditions have to hold. The entry must be a plain nickname, because a mask has no server side form, and the network must be soju backed. On ZNC, on another bouncer, or on a direct connection there is nothing to write to, so the entry stays on that machine. Every row on the settings page says which of the two it is.

    Stronger than ignore

    An ignore is local, so the sender still reaches your connection and you simply do not see it. /accept works the other way on networks with caller ID mode (+g), telling the server not to deliver private messages at all unless you have allowed the sender.

    Chatting

    Notify List

    Watch for nicknames coming online and dropping off, on each connected network. Found at Settings > Chatting > Notify List.

    Adding an entry

    /notify Alice toggles a nick on the active network's list. A trailing comment is saved with the entry, so /notify Alice friend from Libera gives you something to read in six months when you have forgotten who she is. Plain /notify opens the list.

    How it watches

    Where the server supports the IRCv3 MONITOR capability, SeraphIRC registers the list and the server pushes a line the moment somebody appears or leaves. Where it does not, the client falls back to polling with ISON once a minute. Either way you get the same events, the fallback is just slower to notice.

    Scope

    The list is per network, like the ignore list. The same nickname on two networks is two entries, which is correct, since it is very likely two different people.

    Notify is about presence, not messages. To be alerted when somebody talks, see Sounds and Alerts.

    Chatting

    Send Guard

    Send Guard holds a message and asks first when it looks like a mistake IRC cannot undo: a password heading for a channel, or a message heading for the wrong window. It lives at Settings > Chatting > Send Guard and is on by default.

    Nothing leaves your computer

    Every rule runs locally. There is no service being asked whether your message looks like a credential.

    What a hold looks like

    The message does not send. A banner appears saying which rule caught it and showing at most four characters of the matched text, enough to tell you which of the things you pasted was the problem. It is capped at four because the banner is on screen during exactly the screen shares that leak a credential in the first place.

    KeyDoes
    Ctrl+EnterSend anyway (Cmd+Enter on macOS)
    EscapeDelete the line
    EnterNothing. Confirming is deliberately a chord, so muscle memory cannot send it for you.

    A hold you never answered is discarded after ten minutes. A decision you walked away from an hour ago is not a decision, and the channel it was headed for may have turned over completely since.

    It hooks the connection, not the composer

    Every route by which composed text can reach IRC passes through the guard: the composer, /msg, /notice, /me, /raw, /znc, the service commands, and any alias that expands into one of them. A long message is judged whole, before it is split, so a message caught by its second line never has its first line already delivered.

    The client's own traffic is never held. Chat history requests, NickServ auto identify, bouncer probes, typing indicators, and protocol verbs are not composed text and go straight out.

    Chatting

    What It Checks

    Three categories, each with its own switch, plus two shared thresholds. Turning a category off turns off everything inside it.

    Secrets Guard

    On by default. Holds messages that look like passwords, API keys, private keys, or connection strings before they reach a channel.

    Nested inside it is High-entropy tokens, also on, which holds long random looking text matching no known key format. It is the only check that can catch a credential with no recognizable prefix, such as an AWS secret key. It guesses, so it is the rule most likely to be wrong. It applies in every channel and every query.

    Nothing that catches a credential is gated on channel size. A leaked key is equally spent in a channel of five and a channel of fifteen hundred.

    Misdirected messages

    On by default. Holds a message addressed to somebody who is not in this channel, or one that starts with a command word missing its slash, like msg bob ....

    Nested inside it is Short messages in big channels, which is off by default and openly speculative. It holds short messages containing "you" in a big channel, guessing they were meant for one person. Expect it to be wrong sometimes.

    Large pastes and truncation

    On by default. Asks before flooding a channel with a paste, and says so when a message is too long for one line and will arrive as several.

    Both checks switch themselves off on networks supporting IRCv3 multiline, where a long or pasted message goes as one message with its line breaks intact. They come back if a message exceeds even what that network sends as one, because past that point it does arrive in pieces again.

    Chatting

    Exceptions

    Two kinds, and they are very different in scope. One quiets a single check, the other switches the guard off entirely.

    Message prefix exceptions

    bob: see this link and example: see this link are the same shape, so no tuning can tell them apart. Instead you name the prefixes you use for prose. A message starting with one is never read as addressing somebody.

    This only relaxes the wrong window check. Credential and large paste checks still run on the rest of the line, so a key after the prefix is still held.

    Per channel exceptions

    These turn Send Guard off entirely in one channel or query. Add one from the settings page with the button that names the buffer you were last looking at. It is scoped that way on purpose, because a free text field invites a typo that silently matches nothing, which for a safety setting means believing you switched it off somewhere you did not.

    The list groups entries under their network, since #general exists on more than one and "which one?" is not a question worth squinting at for a setting like this.

    A per channel exception disables the credential checks too. If you only want to stop being asked about a prefix you use often, add a prefix exception instead.

    Network

    Bouncer Profiles

    A profile is one bouncer, saved once and reused by every network that connects through it. Found at Settings > Network > Bouncer Profiles.

    Why profiles exist

    A bouncer usually fronts several IRC networks. Without profiles you would retype the same host, port, and credentials for each one. Save it once instead, then point networks at it. Each profile lists the networks currently using it.

    What a profile holds

    FieldNotes
    Profile NameWhat you will see when picking it on a network.
    TypeSoju, ZNC, or Custom IRC bouncer. Soju unlocks network discovery, covered below.
    Host and PortWhere the bouncer listens.
    TLS enabledOn unless you have a reason. The port default follows this setting.
    Hosting / TrustSelf hosted or third party. See below.
    Username and PasswordThe password goes to the operating system credential store, never into the config file.
    NotesFree text for your own benefit.

    There is a Test Connection action, so you can find out the host is wrong before a network depends on it.

    Self signed certificates

    A bouncer you run yourself often presents a certificate no public authority signed. The profile can trust that specific certificate, recording its fingerprint, subject, issuer, and validity dates. Trust is pinned to that one certificate rather than switching verification off, so a different certificate appearing later is still caught.

    Third party hosting. A bouncer you do not run can see the IRC traffic passing through it, including channel messages, private messages, metadata, and credentials sent over that connection. Use a host you trust. For maximum privacy, self host.

    Soju network discovery

    On a Soju profile SeraphIRC can ask the bouncer which networks it already has configured and import them, rather than making you recreate each one by hand. See Using a Bouncer.

    Deleting

    A profile still in use by a network cannot be deleted. The confirmation names the networks holding it, so you know what to repoint first.

    Network

    DCC Transfers

    The classic IRC file transfer, computer to computer with no server in between. Settings live at Settings > Network > DCC Transfers, and the commands are under /dcc.

    DCC needs a direct connection, so it is unavailable on networks that go through a bouncer. If none of your networks are direct, the settings page says so rather than letting you tune something that cannot run. Seraph Transfer is the option that works from behind one.

    Where files land

    Save received files to a directory of your choosing, with a Browse button. Left empty it uses the platform default.

    Off by default, and worth understanding before switching it on. When enabled, four lists decide what gets taken without asking.

    In the client

    Network

    Seraph Transfer & Chat

    A peer to peer transport that uses a rendezvous server to get through routers and firewalls, encrypts the transfer, and checks the file against a hash on arrival. Unlike DCC it works from behind a bouncer, because the bouncer is never in the data path. Settings > Network > Seraph Transfer & Chat.

    Seraph Transfer is peer to peer, so the other end can see your real IP address. Sending an offer reveals it to the rendezvous immediately, and to the other person once they accept.

    The two things it powers

    • /seraphtransfer nick offers a file. No upload host and no copy left behind.
    • /seraphchat nick opens a direct encrypted conversation. Nothing said in it is written to disk on either side, and closing the window discards it.

    Both are also on a nickname's right click menu. The rendezvous server brokers the connection and sees your IP address for that purpose, but not the data flowing between you.

    Settings

    SettingWhat it does
    Rendezvous serviceWhich broker to use, with a test button for reachability.
    Save received files toWhere accepted files land.
    Largest file to accept (MB)An offer states its size, so one over the limit is refused before anything connects. You get a line in the conversation rather than an offer. Sending is checked too, so you cannot start a transfer the other end will refuse. 0 uses the default.
    Transfers at onceConcurrency cap.
    Keepalive (seconds)How often the connection is nudged so routers do not forget it. Too long and a home router drops it, which looks like a transfer stalling with no error. 0 uses the default.
    Send explicit declinesOff by default. Declining silently sends nothing at all, so an unwanted offer cannot be used to confirm you are at the keyboard. Turning it on tells people you said no, at the cost of confirming you saw it.

    Remembered Peers

    The client records the identity each person presented the first time you transferred with them. If it ever changes you are warned, which catches somebody impersonating them later.

    It cannot catch somebody who was already in the way on that very first transfer. To be certain, read your fingerprints to each other somewhere other than IRC, and compare all of it. A partial match is not a match.

    Forgetting a peer makes your next transfer with them count as a first one, so a changed identity will not be flagged.

    DCC is still there

    Seraph Transfer is newer and its traversal can fail on networks it cannot get through. DCC stays reachable as a deliberate choice rather than something hidden once the new one exists.

    Text Formatting

    Formatting Overview

    Two input syntaxes compile to standard IRC control codes, so other clients see ordinary formatting rather than your markup.

    The two syntaxes

    Markdown is inline only. This is IRC formatting parity rather than CommonMark, so no headings, lists, quotes, tables, fenced code blocks, images, or links. Tokens are a superset that adds what markdown cannot express: underline and color.

    Both can appear in the same message. They compile to the same bytes.

    Turning it on

    ScopeHow
    One message/format or /f, with /format-me, /format-msg, and /format-notice variants
    One message, off/plain, with the same -me, -msg, and -notice variants
    AlwaysSettings > Preferences > Chat sets auto_format to off, markdown, or markdown plus tokens as you type

    Spoilers

    IRC has no spoiler control code. Rather than the black on black trick, SeraphIRC puts the literal ||text|| on the wire and renders it click to reveal locally. Other clients see readable pipes.

    Spoiler content is literal, like a code span, and the markers need non whitespace directly inside them, so pasted code such as if (a || b) is never mistaken for one.

    Markdown Syntax

    Inline markers only. Block level CommonMark is not part of IRC formatting and stays literal.

    Emphasis is underscores

    Asterisks are never markers. Underscores follow CommonMark style strict flanking, which keeps snake_case_word and http://example.com/a_b_c literal.

    Example

    /f __Heads up__: the meeting moved to _Thursday_.
/f Run `git status` before you push.
/f The killer was ||the butler||.

    Text Formatting

    Token Syntax

    Tokens start with $. They exist because markdown has no way to say underline or color.

    TokenEffect
    $b … $bBold
    $i … $iItalic
    $u … $uUnderline
    $s … $sStrikethrough
    $m … $mMonospace
    $c<n> … $cForeground color
    $c<n>,<m> … $cForeground on a background

    Tokens are toggles

    Each token flips its attribute on or off, exactly like the wire byte it compiles to, so ranges may overlap instead of nesting. $ba $ib $bc $i renders bold "a ", bold italic "b", italic "c". Markdown cannot express that.

    Example

    /f $uPlease read this$u before opening a ticket.
/f $c04Build failed$c on the release branch.
/f $c00,02 NOTICE $c the channel is moderated until Monday.

    Text Formatting

    Rules and Escapes

    The parsing rules exist so ordinary text, especially pasted code and paths, comes out the way you typed it.

    What stays literal

    • Code spans win. Formatting inside `…` is suppressed, so `not __bold__ here` sends the underscores.
    • Unterminated markers. __bold with no closer is literal.
    • Empty spans. ____ and $b$b produce nothing.
    • Flanking. snake_case_word and URLs with underscores are left alone.

    Escaping

    A backslash before a formatting character makes it literal: \* \_ \~ \` \| \$ and \\. Before anything else the backslash is itself literal, so C:\path\to\file needs no doubling. Escapes survive a round trip.

    Line length

    Control bytes count toward the 512 byte IRC line limit. A split never cuts inside a control sequence, and every active attribute is reopened at the start of each continuation line.

    On the Wire

    What actually leaves your computer. For anyone writing a bot, debugging a relay, or wondering why a message looks different elsewhere.

    AttributeByte
    Bold0x02
    Italic0x1D
    Underline0x1F
    Strikethrough0x1E
    Monospace0x11
    Color0x03, two digit padded
    Reset0x0F, accepted inbound, never sent

    Why no trailing reset

    Every attribute is closed with its own toggle byte rather than one reset at the end of the line. If a server or relay truncates the message, the formatting cannot leak into what follows.

    Inbound

    Control codes from other clients are decoded into styled spans and rendered through your active theme.
